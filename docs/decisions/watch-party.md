# Architecture Decision Record: Live Watch Party Rooms (Multiplayer Synced Cinema)

## Status
Accepted & Implemented

## Context
Media Vault already streams local-drive, single-part Telegram MTProto, and >2 GB multi-part Telegram media through a unified HTTP Range pipeline backed by a thread-safe two-tier hot-block cache (`app/stream_cache.py` + `app/media_ops.py`). Users want to co-watch videos with friends across phones and laptops in temporary rooms with synchronized play/pause/seek/playback-rate, Up Next queues, participant presence, live chat, and floating reactions—without ever sharing `WEB_AUTH_TOKEN` or exposing any vault media outside the room's explicit queue.

## Key Architectural Decisions
1. **Ephemeral In-Memory Room & Sync State Engine (`app/watch_party.py`):**
   - Active rooms, participants, bounded chat history (`collections.deque(maxlen=100)`), and WebSocket connections are stored in memory inside `WatchPartyService` (wired onto `AppContext` and started/stopped in `app/main.py` lifespan).
   - **Why in-memory over SQLite:** Watch Party rooms are ephemeral live sessions with short-lived guest tokens and active WebSockets; in-memory storage avoids SQLite write contention during rapid playback/chat events and ensures server restarts naturally invalidate old guest tokens. Media metadata is resolved live from `ctx.db.get_media()`, and `delete_media_item()` in `app/media_ops.py` notifies `ctx.watch_party.handle_media_deleted()` so deleted vault items are immediately pruned from active rooms.
   - **Authoritative Monotonic Clock:** Playback position is anchored to `(position_sec, state_updated_mono, playback_rate, is_playing)` with monotonic `state_seq` revisions. Newly joining clients receive `position_sec` computed as `effective_position = position_sec + max(0.0, now_mono - state_updated_mono) * playback_rate` (clamped to item duration when known) paired with UTC `server_time_ms` for RTT-compensated sync.
   - **Optional Wait-for-Buffering Coordination:** Rooms support `wait_for_buffering: bool = False`. When enabled and playing, a peer entering `buffering` pauses the room at its exact `effective_position` and auto-resumes once all connected peers report `ready`.
2. **Strict Security Isolation & Zero `WEB_AUTH_TOKEN` Exposure:**
   - Host management endpoints (`/api/watch-party/rooms*`) require `Depends(require_auth)`.
   - Room creation and guest `/join` issue random 256-bit room-scoped tokens (`secrets.token_urlsafe(32)`), stored only as SHA-256 digests and verified in constant time via `hmac.compare_digest`. `WEB_AUTH_TOKEN` is never accepted as a room token and never exposed to guests or `/watch/{room_code}`.
   - Optional room PINs (4–32 chars) are salted per room and hashed with PBKDF2-HMAC-SHA256 (`100,000` iterations) and verified via `hmac.compare_digest`. Plaintext PINs are never persisted or echoed.
   - `GET /api/watch-party/{room_code}/info` returns generic `"title": "Protected Watch Party"` when `requires_pin=True` (zero private title, filename, path, folder, tag, or URL leakage before PIN verification) and returns `{"active": false}` for closed/expired/unknown rooms.
   - Scoped media and thumbnail proxies (`GET/HEAD /api/watch-party/{room_code}/media/{media_id}/stream` and `/thumb`) strictly require a valid, non-revoked token for that exact `room_code` AND `media_id ∈ queue ∪ {active_media_id}` (`403 Forbidden` otherwise). Removing an item from the queue, kicking a guest, expiring a room, or closing a room immediately revokes media access.
   - `GET/HEAD /stream` reuses `resolve_media_source()`, `_parse_range_header()`, `prefetch_multipart_first()`, and `iter_source_range()` from `app/media_ops.py` so simultaneous viewers share the two-tier hot-block cache and fetch each Telegram chunk only once. `HEAD` resolves size from local `stat()` or SQLite metadata with zero Telegram RPCs.
3. **WebSocket Transport, Rate Limiting & Hardening (`app/routers/watch_party.py`):**
   - Primary authentication uses **first-message auth** (`{"type": "auth", "token": "..."}` within 5 s of connect) so tokens stay out of WebSocket URLs and proxy access logs, with optional `?wp_token=` fallback for lightweight clients.
   - Bounded frame size (`8192` bytes), non-text/binary frame rejection, `math.isfinite()` validation on numeric playback fields, per-participant WS frame / chat / reaction rate limits, and bounded per-socket send/close timeouts (`2.0 s`) prevent slow-consumer or flood DoS.
   - Hardened per-IP PIN and join rate limiters fail closed if map caps (`4096` keys) saturate with active buckets rather than evicting active buckets; missing-PIN probes count against the PIN budget; never-connected HTTP ghost joins are reclaimable after a 30 s grace window.
4. **Zero-Build Standalone Guest UI & Host Cinema Bridge:**
   - `GET /watch/{room_code}` serves `static/watch-party.html` + `static/css/watch-party.css` + `static/js/watch-party.js` with strict CSP (`script-src 'self'; style-src 'self'; media-src 'self' blob:; connect-src 'self' ws: wss:; frame-ancestors 'none'`). Zero inline scripts/styles/event handlers; all dynamic text rendered via `textContent` (zero `innerHTML` sinks); floating reactions use CSS lane classes (`.wp-lane-0`..`.wp-lane-5`).
   - Client drift correction combines 3-ping burst + 15 s periodic RTT clock-offset estimation with three-zone sync (`< 0.45 s` ignore, `0.45–1.5 s` gentle `±5%` `playbackRate` nudge, `> 1.5 s` hard seek with feedback-loop suppression) and an explicit "Click to Sync & Unmute" overlay when browser autoplay is blocked.
   - Host Cinema integration (`static/js/features/watch-party-host.js` + minimal hook in `static/js/features/cinema.js` and `static/index.html`, keeping `index.html` at 347 lines `< 350`) lets the host create/manage rooms directly from Cinema, bidirectionally sync the Cinema `<video>` player with guests, and open `/watch/{room_code}` in a new tab via a self-cleaning 15-second same-origin `localStorage` handoff (`wp_handoff_<room_code>`) into `sessionStorage` without putting tokens in the URL.

## Design & Deviation Ledger

| Reference Plan Item | What Was Actually Built | Why We Followed or Departed | Known Risks / Follow-ups |
|---|---|---|---|
| In-memory room registry vs lightweight SQLite persistence + TTL idle reaper | Purely in-memory `WatchPartyService` registered on `AppContext` with background idle/TTL reaper started & cleanly stopped in `app/main.py` lifespan, plus `delete_media_item()` cleanup hook in `app/media_ops.py` | Followed (chose in-memory over SQLite): avoids DB write contention during real-time sync/chat, keeps restarts fail-safe by invalidating ephemeral guest tokens, and queries live `media_items` metadata on demand | Server restart terminates active Watch Parties (clients show "Watch Party Ended"); acceptable for temporary co-viewing rooms |
| High-entropy `room_code`, salted/hashed PIN (`hmac.compare_digest`), room-scoped tokens (never `WEB_AUTH_TOKEN`), `host_only` vs `everyone` | `secrets.token_urlsafe(9)` codes, per-room 16-byte salted PBKDF2-HMAC-SHA256 PINs, 256-bit room tokens stored as SHA-256 digests (`hmac.compare_digest`), plus `POST /api/watch-party/rooms/{code}/host-session` for multi-tab host reconnects | Followed + hardened: storing token digests and supporting multiple host sessions (capped at 5) lets the host run both Cinema sync and `/watch/{code}` without ever touching `WEB_AUTH_TOKEN` | When `WEB_AUTH_TOKEN` is intentionally empty (trusted LAN/Tailscale mode), host management routes follow existing `require_auth` fail-open semantics; set `WEB_AUTH_TOKEN` for internet-exposed vaults |
| Non-sensitive `GET /api/watch-party/{code}/info` before PIN verification | Returns generic `"title": "Protected Watch Party"` when `requires_pin=True`, real title only when open, `active: False` for unknown/expired rooms; never returns filenames, paths, folders, tags, or URLs | Followed + hardened: satisfies strict pre-PIN non-leakage invariant #2 while giving the join UI clean active/PIN/occupancy status | `participant_count` is still returned on `/info` per spec; if stricter occupancy privacy is ever wanted on PIN-locked rooms, it can be zeroed pre-PIN |
| `POST /join` PIN brute-force rate limit & capacity bounds | Per-`(room_code, client_ip)` PIN bucket using `request.client.host` (no spoofable `X-Forwarded-For`), missing-PIN probes counted (review H4), fail-closed cap when rate maps saturate (review H2), and 30 s grace window before reclaiming never-connected HTTP ghost joins (review H1) | Followed + strengthened after adversarial review: eliminates active-bucket flush attacks and ghost-join capacity DoS while preserving clean `409` behavior for concurrent legitimate joins | Behind a reverse proxy where all traffic shares `127.0.0.1`, per-IP buckets aggregate proxy traffic; adding a trusted-proxy CIDR setting is a natural future enhancement |
| `WS /api/watch-party/{code}/ws` sync, ping/pong, chat, reactions, kick, buffering | Supports first-message `auth` (primary, zero URL token logging) + `?wp_token=` fallback, `ping`/`pong`, `play`/`pause`/`seek`/`rate`/`select_item`, host-only `queue_update`/`update_settings`/`kick`/`close_room`, optional `wait_for_buffering` auto-pause/resume, bounded chat ring buffer (100), allowlisted ephemeral reactions, 8 KiB frame cap, binary-frame guard, and `math.isfinite()` float checks | Followed + refined: adding host-only WS `update_settings` and `close_room` allows the host tab on `/watch/{code}` to toggle controls/buffering or end the party without needing `WEB_AUTH_TOKEN` | Broadcasts await all sockets concurrently with a 2 s per-socket timeout; a single stalled client adds at most 2 s latency to that broadcast tick before being skipped |
| Scoped `GET/HEAD /stream` & `/thumb` reusing `app/media_ops.py` | Strictly enforces room-token auth + `media_id ∈ queue ∪ {active_media_id}` (`403` otherwise), `Cache-Control: private, no-store`, `Referrer-Policy: no-referrer`, zero-RPC `HEAD`, full `200`/`206`/`416` Range streaming via `app/media_ops.py`, and basename + `is_relative_to()` thumb containment (review L2); queue replacement always revokes excluded active items (review M1) | Followed + hardened: guarantees immediate IDOR revocation on queue removal/kick/close while keeping multi-viewer Telegram hot-block caching intact | `<video>` elements require `?wp_token=` in stream URLs (since browsers cannot set `Authorization` headers on `<video src>`), so reverse proxies should avoid logging full query strings on `/api/watch-party/` |
| Host Cinema UI (`cinema.js` + `index.html`) + standalone guest UI (`watch-party.html/js/css`) | Modular host UI in `static/js/features/watch-party-host.js` wired via minimal hook in `cinema.js` and 1 button in `index.html` (347 lines `< 350`), cross-tab host handoff via 15 s self-cleaning `localStorage` bridge (`wp_handoff_<code_>`, review H3), and strict-CSP standalone `/watch/{code}` page with zero inline styles/scripts and `textContent`-only rendering | Followed + modularized: keeps `index.html` under the 350-line test threshold, avoids browser `noopener` `sessionStorage` loss when opening `/watch/{code}` in a new tab, and passes strict `style-src 'self'` CSP via CSS lane classes | Main vault `/` page does not yet set a strict CSP header (pre-existing architecture); guest `/watch/{code}` enforces full strict CSP |
